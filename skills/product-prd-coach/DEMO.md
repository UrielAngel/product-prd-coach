# 完整演示：从一个迭代需求到可评审 PRD

> 本文件用于演示流程，也用于自检 skill 是否按预期工作。
> 示例产品为虚构的 C 端记账 App「悦记账」，任何雷同纯属巧合。

## 演示场景

**需求原话**（老板在群里发的一句话）：

> 「下个版本加个批量导入账单的功能，用户抱怨一笔笔记太麻烦。」

这是一句典型的不完整需求：没说从哪导入、支持什么格式、失败怎么处理、和现有预算/账本怎么衔接。

---

## 先做对比：同一个需求，两种 AI

**没有基准文件的通用 AI 会写出这种东西：**

```
6.3 异常处理
导入失败时提示"导入失败，请重试"。
每行数据校验不通过时跳过该行，继续导入剩余数据。
导入完成后显示成功条数。
```

问题逐条清点：

| 句 | 问题 |
|----|------|
| 提示"导入失败，请重试" | **编造**。该产品错误文案规范明确要求「说清怎么改」，且该文案从未被人确认过 |
| 跳过该行继续导入 | **编造**。真实的取舍应由 PM 决定：是跳过还是整批中止，涉及用户对账预期 |
| 显示成功条数 | **不完整**。没说失败行去哪看、能不能导出错误清单 |

三句话，三个编造。评审时会被逐条打回——这就是"看起来完整但不可用"。

**本 skill 会写出这种东西：**

```
6.3 异常处理
导入执行方式（沿用《feature-inventory》3.1 批量操作规范）：
  - 校验粒度：【待确认：整批校验失败即中止 / 逐行跳过】
  - 失败反馈：沿用 interaction-spec「失败态」统一表现 + 提供「下载失败明细」入口
  - 错误文案：遵循文案规范第 4 条，须说明具体原因与修正方式（如"第 3 行日期格式应为 YYYY-MM-DD"）
```

差别在于：**它知道自己不知道什么。**

## 完整流程演示

### 步骤 1｜阶段 B：加载基准文件

**AI**：检测到项目已有 `baseline/`。已读取：产品概述（记账 App 悦记账 v3.2.0）、功能清单（5 模块 18 项功能）、交互规范、术语表。
确认本次迭代是否沿用当前基准？

**用户**：沿用。

> 演示要点：这一句替代了过去需要重复 20 分钟的产品背景解释。

### 步骤 2｜阶段 0：澄清背景（AI 反问）

**AI**：需求我先理解为「支持用户批量导入账单」。有三件事会直接影响方案，请确认：

1. 数据来源是什么？（如支付宝/微信账单 CSV、Excel 模板、其他 App 导出）
2. 谁会用这个功能？日常记账用户还是之前用别的 App、现在迁移过来的用户？
3. 本期成功标准怎么定？（如"迁移用户次日留存提升 X%"或"导入成功率 > 95%"）

**用户**：先支持支付宝和微信的 CSV。是给迁移用户用的。成功标准是导入完成率超过 80%。

> 演示要点：**每轮不超过 3 个问题，问的是真正阻塞的点**，不是走流程式地追问背景与目标。

### 步骤 3｜反补基准 + 阶段 1：范围界定

**AI**：已把「批量导入」作为新功能反补进 feature-inventory，新增术语「迁移用户」写入 glossary。
本期范围建议：

| 分级 | 内容 |
|------|------|
| Must | 支付宝/微信 CSV 解析、字段映射、结果预览、确认导入 |
| Should | 失败明细下载 |
| Could | 自动识别账单来源（无需用户选） |
| Won't | 其他 App 格式、PDF 账单（写明原因：格式不统一，本期验证重点在于主流程跑通） |

确认吗？

**用户**：同意，但 Could 提到下一期。

### 步骤 4｜阶段 2：方案设计（含 HTML 原型）

**AI**：方案骨架如下，确认后我生成 HTML 原型：

- 入口：记账 → 右上角「导入」→ 选择来源
- 主流程：选来源 → 上传文件 → 字段映射预览 → 确认 → 导入 → 结果页
- 异常分支：格式不符 / 文件解析失败 / 重复数据（同一时间+金额+商户判重）/ 部分成功

一个问题：**重复数据怎么处理？** 基准文件里没有「导入场景去重」的既有规则。选项：跳过 / 覆盖 / 由用户在预览页逐条勾选。

**用户**：预览页让用户勾选。

> 演示要点：**AI 发现基准里没有对应规则，主动问而不是自己定。** 这就是「反问优先 → 复用基准」的排序在起作用。

**AI**：已生成 HTML 原型（含空态/加载/失败/部分成功/极值 5 种状态），归档至 `docs/prototypes/v3.3.0/`。

### 步骤 5｜阶段 3：PRD 撰写

**AI**：识别为 C 端产品，套用专属模块：用户分层与生命周期、埋点与转化漏斗。

已嵌入 5 张原型截图并按 6.2-01 起编号。其中：

- 6.3 异常处理按刚才确认的规则写入，来源标注为「沿用 feature-inventory 3.1 + 用户确认」
- 仍存在 2 项「待确认」：① 单文件最大支持多少条记录 ② 是否需要导入进度百分比

请在评审前补齐这两项。

### 步骤 6｜阶段 4：自检

**AI**：自检结果——

| 组 | 结果 |
|----|------|
| A-F 常规检查（21 项） | 19 通过，2 待补 |
| **G 越界检查** | **5/5 通过** |

越界检查详情：

- 全文无自行补齐内容 ✓
- 衔接处均注明引用来源（如"沿用查询-3.2 订单列表筛选器交互"）✓
- 2 项待确认已在附录列出并指定负责人 ✓
- 新增功能与术语已回写基准 ✓
- PRD 自包含，无"详见原型" ✓

### 步骤 7｜交付

**AI**：已输出 Word 文档，图片随文档嵌入。同时已完成基准文件反补——下次迭代不用再解释一遍这次的内容。

## 演示时建议强调的三个瞬间

1. **步骤 2 的反问** —— 展示"AI 不瞎猜"。这是与其他 AI 写作工具最直观的区别。
2. **步骤 4 的「基准里没这条规则」** —— 展示"它知道自己不知道什么"。这是防越界机制真正生效的时刻。
3. **步骤 6 的越界检查 5/5** —— 展示交付前有机器可验的质量闸门，而不是靠人肉通读。

## 可能被质疑的问题

| 质疑 | 应答 |
|------|------|
| 反问会不会太慢？ | 每轮 ≤3 个问题，且都是阻塞项。真正省下的是返工时间——评审被打回一轮的成本远大于回答 3 个问题 |
| 待确认项太多怎么办？ | 待确认多 = 需求本身不清晰，这是真实反映，不是 skill 的缺陷。而且它们被集中列出，比散落在正文角落里更容易推进 |
| 基准文件要维护多久？ | 首次约 10 分钟，之后每次迭代自动反补。边际成本递减，第 5 次迭代起基本无需额外投入 |
| 不支持 X 原型工具？ | 刻意的设计。交付 PRD 而非原型文件，就是为了不受工具碎片化影响 |
