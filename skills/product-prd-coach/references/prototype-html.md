# HTML 原型产出与嵌入规范

阶段 2（方案设计）与阶段 4（交付）加载本文件。

## 一、为什么不交付原型文件

各 PM 使用的原型工具不同（Axure / 墨刀 / Figma / 即时设计等），AI 直接产出原型文件时产出物与企业规范不兼容，接收方打不开或用不了。

本 skill 的解法：**改变交付物的形态，而不是适配每一种工具。**

```
HTML 原型（生成最快最稳） → 截图为图片/GIF → 嵌入 PRD 对应位置 → 仅交付 PRD 文档
```

**不生成任何原型源文件，不做工具格式转换。** 最终只交付一份 PRD，由在线智慧文档（钉钉 / 飞书 / 企业微信 / Slack 通用）承载，工具差异问题在交付层面被彻底消除。

## 二、HTML 产出规范

多模型实测：让模型一次性生成完整 HTML 页面，比生成 UI 图片、比多轮拼装的原型代码，速度与稳定性都最优。

技术要求：

- **单文件 HTML**：CSS 与 JS 全部内联，一个 .html 文件即可打开，无构建步骤、无外部依赖
- **不要生成孤立的 UI 图片**：切勿让模型额外调用图像生成来"画界面"，那是质量陷阱
- 每个页面一个 HTML 文件，命名 `{页面名}-{版本}.html`，归档到 `docs/prototypes/<版本>/`
- 移动端产品按主流移动 width 呈现（如 390px），并注明设备基准

## 三、必须覆盖的状态

每个界面都要体现在 PRD 截图中，缺一不可：

| 状态 | 必须体现 |
|------|----------|
| 正常态 | 有真实数据时的完整形态（不使用假数据堆砌，但要有代表性数据） |
| 空态 | 无任何数据时的占位文案与引导动作 |
| 加载态 | 骨架屏或 loading 的呈现方式 |
| 错误/失败态 | 失败文案与可执行的重试入口 |
| 极值态 | 超长文本截断、大量数据的截断或分页表现 |

动效用 GIF：页面跳转路径、手势操作、状态过渡这类**静态图无法表达**的部分才做 GIF，其余一律静态截图（GIF 体积大会拖累文档打开速度）。

## 四、截图嵌入规则

截图不是装饰，是 PRD 的文字替代品——它必须落在正确的位置并承担说明职责。

1. **位置**：紧邻对应功能的文字描述，图在上或在右，遵循文档工具的图文规则；严禁所有图堆在文末。
2. **编号**：按 `图 {章节号}-{序号}` 编号（如图 6.2-01），正文引用时必须用编号，不写"上图/下图"。
3. **命名**：图片文件名 `{编号}-{页面}-{状态}.png`，如 `fig6.2-01-order-list-empty.png`。
4. **图注**：每张图下方配一句话说明"这张图说明什么"，重点指出不可从图中直接读出的规则。
5. **GIF 补充**：GIF 下方必须附**文字版的步骤说明**，保证 GIF 加载失败时信息不丢失。

## 五、Word 交付时的处理

最终交付为 Word 文档时（本 skill 的默认交付形态）：

- 图片以嵌入方式插入，随文档走，不依赖外部路径
- 保持"图紧跟其所属说明"的顺序，避免图片浮动导致图文错位
- 原型 HTML 源文件**不作为交付物**，但要告知用户已归档路径，供后续迭代复用

## 六、禁止事项

- 禁止让模型直接生成 UI 图片代替界面
- 禁止输出 Axure/.rp、Figma、Sketch 等需要特定工具才能打开的文件作为交付物
- 禁止把未截图说明的部分留在"见原型"——**PRD 必须自包含**，评审方只看文档就要能理解方案
- 禁止在文档中引用需要登录才能访问的内部链接作为唯一说明
