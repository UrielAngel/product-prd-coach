# 交付与企业文档发布

阶段 4（自检与交付）加载本文件。

## 一、先给价值，再要许可

**发布到企业文档（飞书/钉钉/企业微信/Slack）是可选增强，不是首次使用的必备环节。**

原因：本 skill 面向分发，陌生用户第一次使用时并不知道产出质量如何。在第一步就要求 OAuth 授权（且是"文档编辑权限"这类敏感权限），是转化漏斗上最脆的一环——用户会卡在授权页流失，而不是卡在产出质量上。

正确顺序：

| 次序 | 环节 | 用户付出的成本 | 用户获得的确定性 |
|------|------|----------------|------------------|
| 1 | 首次产出，本地交付 Word/markdown | 零 | 知道这个东西值不值得用 |
| 2 | 交付末尾**问一句**，而非要求 | 点一下 | 决定是否开启自动发布 |
| 3 | 后续会话一键发布到企业文档 | 一次授权 | 省掉每次导出上传的重复劳动 |

首次交付完成后，提示话术方向："这次先给你本地文件。如果希望以后直接发布到飞书/钉钉文档里、省掉手动上传，可以开启对应连接器。——不影响本次使用。"

## 二、能力探测与优雅降级

**本 skill 不得假定任何在线文档能力存在。** 每次交付前按以下顺序判断：

```
检测到可用的在线文档连接器？
├─ 是 → 询问用户是否发布（不默认执行），用户确认后写入企业文档，返回文档链接
└─ 否 → 本地交付。附一句说明：
        "当前环境未检测到在线文档连接器，已按本地文件交付。
         这份 Word/文档可直接导入飞书、钉钉、企业微信等智慧文档，
         内容与在线版一致。"
```

降级必须是**静默且体面**的：不报错、不中断、不反复请求授权。用户拿到的东西始终完整可用。

## 三、为什么还支持本地交付

用户原本的核心洞察依然成立：**智慧文档是最通用的需求沟通载体**（钉钉/飞书/企业微信/Slack 都能承载）。

但"通用性"来自**文档格式**，不来自**自动写入**。本地交付的 Word/文档同样可以：
- 由用户在任意一家办公软件里打开/导入
- 保持一致的结构与 embedded 图片
- 不受连接器可用性限制

因此：**本地交付是基线能力，自动发布是可选增强。** 任何时候删掉增强，基线都完整。

## 四、跨平台约束（重要）

在线文档连接器属于特定平台能力，**不可能在所有 agent 上通用**。因此：

- **本 skill 的免费分发版（L0）必须保持零外部依赖**，确保 Claude Code / Codex / Grok / Gemini CLI / Copilot / Cursor 都能跑；
- 企业文档发布能力仅在支持的平台上生效，且必须按第二节降级；
- 不得因为某个环境没有连接器就阻断流程——这是分发型 skill 的红线。

## 五、关于"生成授权链接/二维码"

skill 本身**无法自行生成 OAuth 授权链接或二维码**——授权是平台的账户体系行为，skill 只能引导用户到连接器入口完成授权。设计话术时按"引导去开启"来描述，不要承诺"我来给你生成一个二维码"，否则用户会发现产品做不到。

## 六、Slack 与其他平台

Slack 通常用于通知分发而非 PRD 正文承载。当目标是 Slack 时，按"发送文档链接 + 摘要"处理，而不是把 PRD 正文灌入消息。
